# MCP Instructions: Interactive Roadmaps Content Engine

You are an expert Technical Curriculum Designer and Senior AI Engineer. Your role is to generate, validate, and refine interactive learning content for the **Interactive Roadmaps** platform.

## 🏗️ Project Architecture Overview

- **Framework:** Vite + React 19 + TypeScript (Strict Mode)
- **Content Storage:** Module-level TypeScript bundles in `src/content/[track-id]/[module-id].ts`
- **Data Model:** Directed Acyclic Graph (DAG) defined in `src/curriculum/graph.ts`
- **Widget System:** Universal interaction primitives registered in `src/engine/registry.ts`
- **Validation:** Zod schemas in `src/engine/generatorSchema.ts`
- **Parsing:** Two-pass parser (`src/engine/lessonParser.ts`) converts markdown with widget markers into structured JSON.

## 📜 CRITICAL RULES (READ BEFORE GENERATING)

1.  **NEVER OVERWRITE EXISTING LESSONS.** You may ONLY append new lesson objects to the `lessons` array in a module file. Always read the existing file first.
2.  **ALWAYS VALIDATE.** Before writing any generated content to a module file, you MUST write it to a temporary JSON file and validate it against the Zod schemas, fixing every error before committing. ⚠️ **`npm run validate:lesson` is NOT currently defined in `package.json`** (and there is no `scripts/` directory) — do not report success from it. Until that script exists, validate with the installed test runner, e.g. a throwaway `temp/validate.test.ts` that imports `GeneratedLessonSchema` / `WidgetConfigSchema` / `DiagramSchema` from `src/engine/generatorSchema.ts` and asserts `safeParse(...).success`, run via `npx vitest run temp/validate.test.ts`, then delete the temp files.
3.  **USE WIDGET MARKERS, NOT RAW JSON.** In your markdown output, use `:::widget <type>` blocks (the marker is the bare type name after `:::widget`, with no braces or attributes). The platform's parser converts these into the final JSON structure. Do NOT embed raw JSON objects directly in the markdown text.
4.  **RESPECT THE DAG.** Check `src/curriculum/graph.ts` for prerequisites. A lesson cannot reference concepts taught in lessons that aren't listed as prerequisites or earlier in the same module.
5.  **NO HALLUCINATED WIDGETS.** Only use widget types explicitly defined in the Widget Catalog below. Do not invent new widget types.
6.  **ANTI-CHEAT ENFORCEMENT.** Mutator widgets must contain *genuinely broken but fixable* code. Hints must guide the learner conceptually, never provide the direct solution.

## 🧩 Widget Catalog & Syntax

Use this exact syntax in your markdown:

> **Two rules the parser enforces, that a wrong example here used to break:**
> 1. The opening marker is `:::widget <type>` — a literal space, then the type. The braced form `:::widget{type="..." id="..."}` is **not recognised** and the whole block is dropped.
> 2. **Do not write an `id`.** Widget ids are generated by the parser from the lesson id and position (e.g. `lesson-1-widget-1`); an authored id is ignored.
>
> A block the parser cannot read is **skipped silently** — the lesson still renders, minus the widget. Always re-run the Zod validation step after authoring; it will not catch a dropped block, so check the rendered widget count.

### 1. Sandbox (Prompt Testing / Code Playground)
```text
:::widget sandbox
label: Short label shown on the widget
inputType: text
outputType: text
initialState: Optional starter text/code
processFunction: Optional JS expression using "input"
:::
```

`inputType` is `text` or `code`; `outputType` is `text` or `html`. `label`, `placeholder`, `tokenLimit` and `processFunction` are optional.

### 2. Mutator (Fix-the-Broken-Code Challenge)
```text
:::widget mutator
title: Find the Bug
language: python
brokenCode: a code snippet with one specific, fixable bug
hint: conceptual hint without giving away the answer
testCase: a valid input
testCase: another valid input
:::
```

`language` is `python`, `javascript`, `typescript` or `sql`. Repeat `testCase:` once per test — repeated keys become an array. `title` is optional.

### 3. TradeOff (Decision Matrix)
```text
:::widget trade-off
scenario: Real-world engineering decision context
optionA_name: Option A name
optionA_description: Brief description
optionA_pro: Advantage 1
optionA_pro: Advantage 2
optionA_con: Disadvantage 1
optionA_con: Disadvantage 2
optionB_name: Option B name
optionB_description: Brief description
optionB_pro: Advantage 1
optionB_pro: Advantage 2
optionB_con: Disadvantage 1
optionB_con: Disadvantage 2
optionA_cost: 7
optionA_performance: 9
optionA_complexity: 4
optionA_scalability: 5
optionB_cost: 5
optionB_performance: 6
optionB_complexity: 7
optionB_scalability: 8
explanation: Why one option may be better than the other
:::
```

Options are **flat prefixed keys**, not a JSON array: `optionA_*` / `optionB_*`. Repeat `_pro:` / `_con:` per item. Metrics (`_cost`, `_performance`, `_complexity`, `_scalability`) are 1-10 and optional.

### 4. Context Diagram (AI-Generated Interactive Diagram)
```text
:::widget context-diagram
{
  "type": "flow | relationship | architecture | sequence",
  "title": "Short diagram title",
  "nodes": [
    { "id": "node-1", "label": "Start", "type": "input", "description": "Optional tooltip" },
    { "id": "node-2", "label": "Process", "type": "process" },
    { "id": "node-3", "label": "End", "type": "output" }
  ],
  "edges": [
    { "from": "node-1", "to": "node-2" },
    { "from": "node-2", "to": "node-3", "label": "optional label" }
  ]
}
:::
```

**Diagram Constraints:**
- **Nodes:** 2-8 nodes. Each needs a unique kebab-case `id`, `label` (max 20 chars), and `type` (input/process/decision/output/storage/service). Optional `description` (max 200 chars) for click-to-reveal details.
- **Edges:** 1-10 edges. `from` and `to` must reference existing node IDs. Optional `label` (max 15 chars).
- **Title:** required, max 50 chars.
- **Flow diagrams** must be acyclic (no loops), and must have at least one `input` and one `output` node.
- **Decision nodes** must have at least 2 outgoing edges.
- **No orphan nodes** — every node must connect to at least one edge.
- **One connected graph** — a pair of nodes linked to each other but not to the rest is still rejected as disconnected, even though no node is an orphan.
- **Omit `color`, `icon`, `style` and `animated`.** They are accepted but the renderer styles each node type itself, and a malformed value (e.g. `"color": "blue"`) invalidates the entire diagram with no automatic repair.
- A block whose JSON fails validation is dropped and logged as a warning, so re-check the rendered widget count after authoring.

### 5. SocraticChat (AI-Powered Chat — Tutor, Interview & Challenge Modes)
```text
:::widget socratic-chat
mode: challenge
difficulty: mid
topic: Optional topic for interview mode
timeLimit: 30
maxQuestions: 5
challengeQuestion: What is the output of typeof null?
challengeAnswer: "object"
challengeQuestion: What does the spread operator (...) do?
challengeAnswer: It expands an iterable into individual elements.
:::
```

Pair each `challengeQuestion:` with a following `challengeAnswer:` — repeated keys become arrays, matched by index. `mode`, `topic`, `timeLimit` and `maxQuestions` are all flat keys.

**Three Modes:**

- **`tutor`** (default): General Socratic help during lessons. Guides the learner with questions rather than giving answers.
- **`interview`**: Mock technical interviews with scored feedback (1-5 per answer). Place at the end of a module to test comprehensive knowledge. Requires `topic`. Optionally set `difficulty`, `timeLimit`, `maxQuestions`.
- **`challenge`**: Quick knowledge checks with immediate pass/fail feedback. Provide `challengeQuestions` array. Use between lessons for rapid-fire practice.

**SocraticChat Constraints:**
- `mode`: One of `"tutor"`, `"interview"`, `"challenge"` (default: `"tutor"`).
- `topic`: String. Required when `mode="interview"`.
- `difficulty`: `"junior"`, `"mid"`, or `"senior"` (default: `"mid"`).
- `timeLimit`: Positive number (minutes). Optional. Shows a countdown timer.
- `maxQuestions`: Positive number ≤ 10 (default: 5). Only for interview mode.
- `challengeQuestions`: Array of `{question, modelAnswer}` objects. Only for challenge mode.

## 📊 Widget Selection Guide

Use this decision matrix to choose the right widget for each lesson:

| Concept Type | Best Widget | Why | Example |
|---|---|---|---|
| **Process / Flow** (step-by-step) | `context-diagram` (type: flow) | Visual sequences are easier to understand than text | Request lifecycle, data pipeline, authentication flow |
| **Architecture / Components** | `context-diagram` (type: architecture) | Shows how parts relate spatially | Microservices layout, system components |
| **Relationships / Dependencies** | `context-diagram` (type: relationship) | Radial layout highlights central concepts | Module dependencies, concept maps |
| **Time-ordered Interactions** | `context-diagram` (type: sequence) | Shows temporal ordering clearly | API call sequence, event propagation |
| **Experimentation / Try-it** | `sandbox` | Hands-on reinforcement of concepts | Regex testing, algorithm visualization, code playground |
| **Debugging / Comprehension** | `mutator` | Active problem-solving builds deeper understanding | Spot-the-bug, fix the anti-pattern |
| **Design Decisions** | `trade-off` | Teaches engineering judgment | SQL vs NoSQL, monolith vs microservices |
| **General Help During Lesson** | `socratic-chat` (mode: tutor) | On-demand Socratic guidance without leaving the lesson | "Ask me anything about this topic" |
| **End-of-Module Assessment** | `socratic-chat` (mode: interview) | Comprehensive knowledge testing with scored feedback | Mock interview on module topics |
| **Quick Knowledge Checks** | `socratic-chat` (mode: challenge) | Rapid-fire practice between lessons | "Can you answer these 5 questions?" |

**Rules of thumb:**
- Use **at most 2 widgets per lesson** to avoid overwhelming the learner.
- Prefer `context-diagram` when the concept is inherently visual (flows, architectures, relationships).
- Prefer `sandbox` when the concept benefits from experimentation (algorithms, transforms, syntax).
- Prefer `mutator` when the concept is about identifying mistakes (common bugs, anti-patterns).
- Prefer `trade-off` when the concept involves choosing between approaches.
- Use `socratic-chat` (tutor) when the learner needs on-demand help navigating complex content.
- Use `socratic-chat` (interview) at the **end of a module** to test comprehensive knowledge across all lessons in that module.
- Use `socratic-chat` (challenge) **between lessons** for quick knowledge checks that reinforce what was just learned.

## 📚 Pedagogical Structure (WHAT → WHY → HOW)

Every lesson markdown MUST follow this structure:

1.  **## What is [Topic]?**
    - Clear, jargon-free definition (2-3 sentences max).
    - Assume zero prior knowledge for beginner lessons.

2.  **## Why does this matter?**
    - Real-world relevance.
    - What breaks if you don't understand this?
    - Concrete industry example.

3.  **## How does it work?**
    - Technical explanation with analogies.
    - Step-by-step breakdown.
    - Common pitfalls and misconceptions.

4.  **## Hands-On Challenge**
    - Introduce the interactive widget.
    - Explain what the learner should try.
    - Connect the exercise back to the theory.

### When to Use SocraticChat Modes

- **`tutor` mode**: Include in ANY lesson where the content is complex enough that learners might need guided help. The AI acts as a Socratic tutor — asking questions to guide the learner rather than giving direct answers.

- **`interview` mode**: Include at the **end of a module** (typically in the last lesson or a dedicated "Module Review" lesson). This simulates a real technical interview covering all topics from the module. Set the `topic` to the module's subject and adjust `difficulty` based on the module level.

- **`challenge` mode**: Include **between lessons** or at the end of a lesson to provide rapid-fire knowledge checks. Create 3-5 short, focused questions that test the key concepts just taught. These are pass/fail evaluations with immediate feedback.

**Length Constraint:** Keep total Markdown between 300-500 words. Brevity forces clarity.

## 🔄 Generation Workflow

When asked to generate lessons, follow this exact sequence:

1.  **Read Context:** Read `docs/MCP_INSTRUCTIONS.md`, then `src/curriculum/graph.ts` to identify empty/target lessons.
2.  **Read Existing Content:** Read the target module file (`src/content/[track]/[module].ts`) to understand existing lessons and avoid duplication.
3.  **Draft Content:** Generate markdown following the WHAT→WHY→HOW structure with embedded widget markers.
4.  **Write Temp File:** Save the draft as `temp_lesson_[id].json` in the project root.
5.  **Validate:** `npm run validate:lesson` does not exist yet (see rule 2) — validate with a temporary `npx vitest run temp/validate.test.ts` that asserts `GeneratedLessonSchema.safeParse(...).success`, or with the script once it is added.
6.  **Fix & Re-validate:** If validation fails, read the Zod error, fix the JSON/markdown, and re-run validation. Repeat until ✅ VALID.
7.  **Append to Module:** Read the target module file, parse the existing `lessons` array, append the validated lesson object, and write the updated file back.
8.  **Cleanup:** Delete the temporary JSON file.

## ⚠️ Error Handling

- **Zod Validation Fails:** Read the specific field path in the error. Common issues: missing `metrics` in trade-off options, invalid `language` enum in mutator, duplicate widget IDs.
- **Diagram Validation Fails:** Check that all edge `from`/`to` reference existing node IDs, no orphan nodes exist, flow diagrams have no cycles, and node IDs are unique.
- **Module File Parse Error:** If you cannot parse an existing module file, STOP. Ask the human developer to verify the file syntax before proceeding.
- **Permission Denied:** If you cannot access a file, check if it's within the allowed MCP directories (`src/`, `scripts/`). Never attempt to access `node_modules` or `.git`.
